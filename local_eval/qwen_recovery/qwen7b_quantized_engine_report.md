# Qwen7B Quantized Engine Candidate — Phase 12, Section 2/3 — Result: NO-GO

**Verdict: NO-GO on this server's Tesla P40.** All three candidates in the
required priority order (AWQ → GPTQ → bitsandbytes) were actually tried, not
assumed. None produces a demo-usable engine on this GPU. Per the explicit
instruction to "stop tuning it endlessly and report it as NO-GO" once a
candidate fails, tuning was stopped after the third candidate rather than
continuing to chase further bitsandbytes variants (e.g.
`llm_int8_enable_fp32_cpu_offload=True`, untried).

The working `reference_fp32` engine (~315-320s/call, CPU-offloaded, see
[qwen7b_sequential_stability_report.md](qwen7b_sequential_stability_report.md))
remains the only DEFAULT-selectable engine and is unaffected by this finding.
`quantized_bnb_nf4` is implemented and selectable via `QWEN7B_ENGINE=quantized_bnb_nf4`
(`backend/services/qwen7b_vision_analyzer.py`) for future re-validation on
different hardware, but is never the default and is documented here as
non-functional on this GPU.

## Candidate 1: AWQ (priority order #1) — BLOCKED (tooling, not proven a hardware limit)

Model: `Qwen/Qwen2.5-VL-7B-Instruct-AWQ` (confirmed real, official Qwen
release, verified via `huggingface_hub.model_info()`).

- **Load**: succeeds. 6.95GB VRAM, **zero CPU offload needed** (fits
  entirely on the P40's 24GB). Load time ~5-65s across repeated tests.
- **Generation**: fails. First hit the same cuDNN conv3d issue as the fp32
  engine (`GET was unable to find an engine to execute this computation`) —
  fixed the same way, `torch.backends.cudnn.enabled = False`.
- After that fix, generation still fails: AWQ's GEMM kernel
  (`awq_gemm_triton`) JIT-compiles via Triton at first call, which requires
  `Python.h`:
  ```
  fatal error: Python.h: No such file or directory
  ```
  This server has no `python3.12-devel` package and no root/sudo access
  (`sudo -n true` → password required). Searched the filesystem directly for
  any `pyconfig.h` (the platform-specific header Python.h depends on) —
  none found anywhere, including inside a downloaded Python 3.12.11 source
  tarball (which only ships the generic header; `pyconfig.h` is generated by
  running `./configure`, i.e. a full build would be needed).
- Tried the precompiled alternative, `autoawq-kernels` (avoids Triton JIT
  entirely). This **broke the working environment**: it pulled in
  torch 2.13.0 as a transitive dependency, which does not support this P40
  (sm_61; torch 2.5+ dropped Pascal). Uninstalled it and reinstalled
  `torch==2.4.1+cu118`/`torchvision==0.19.1+cu118`, then re-verified the fix
  with a standalone CUDA matmul smoke test before continuing.
- **Conclusion**: AWQ is blocked by this server's missing dev headers and
  lack of root access, not disproven as a working quantization method in
  general. If a future environment has `python3.12-devel` (or root to
  install it) or ships prebuilt Triton kernels compatible with torch 2.4.1,
  AWQ should be retried first — it is the only candidate here that needed
  zero CPU offload.

## Candidate 2: GPTQ (priority order #2) — UNAVAILABLE

Checked both `Qwen/Qwen2.5-VL-7B-Instruct-GPTQ-Int4` and
`Qwen/Qwen2.5-VL-7B-Instruct-GPTQ-Int8` via
`huggingface_hub.model_info(...)`. Both return `RepositoryNotFoundError` —
no official pre-quantized GPTQ checkpoint exists for this vision-language
model. Not attempted further per the instruction to use pre-quantized
checkpoints only, not to GPTQ-quantize the fp32 checkpoint ourselves in the
time available.

## Candidate 3: bitsandbytes nf4 (priority order #3, fallback) — LOADS AND RUNS, BUT OUTPUT IS BROKEN

Dynamically quantizes the real `Qwen/Qwen2.5-VL-7B-Instruct` fp32 checkpoint
at load time via `BitsAndBytesConfig(load_in_4bit=True,
bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True,
bnb_4bit_compute_dtype=<dtype>)`. `bitsandbytes==0.49.2` installs cleanly
without disturbing the torch/torchvision versions needed for this GPU.

Real measurements, same real image (`water_001.png`), `device_map="auto"`,
`attn_implementation="eager"`, `cudnn.enabled=False`:

| compute_dtype | VRAM allocated | load time | gen (cold) | gen (warm) | output |
|---|---|---|---|---|---|
| float16 | 5.9GB | ~30s | 34.3s | 33.4s | `'!! The!!!!! !!! !! ! ! ! ! ! ! ! ...'` (degenerate) |
| float32 | 5.9GB | ~30s | 7.2s | 6.9s | identical degenerate `!`-token garbage |

Both configurations are fully GPU-resident (no CPU offload) and both
produce the **same broken output** regardless of compute dtype. This is a
meaningful finding: it rules out "fp16 compute" alone as the root cause —
even a full fp32 dequantize-and-compute path produces the same garbage when
the model is fully GPU-resident on this Pascal card. The one config that
does produce correct output (`reference_fp32`) is CPU-offloaded by
necessity (28GB fp32 doesn't fit in 24GB VRAM). This suggests, as a
hypothesis only (not confirmed), that some part of this model's
generation/attention path has a GPU-resident-specific bug on this
architecture (compute capability 6.1) that the CPU-offloaded path happens
to avoid — not a simple precision issue.

One further diagnostic (forcing bnb to offload some layers to CPU via
`llm_int8_enable_fp32_cpu_offload=True`, to test offload-vs-dtype in
isolation) was identified but not run — stopped here per the explicit
instruction not to keep tuning indefinitely once NO-GO is reached, and
because achieving CPU offload with bnb would negate the entire reason to
use bnb (speed), landing back at roughly the same latency as
`reference_fp32` while adding quantization-accuracy risk for no gain.

## Recommendation (per Section 11's own prescribed fallback)

Do not spend further time micro-optimizing quantization on this P40. The
`Qwen7BVisionAnalyzer` engine interface (`backend/services/qwen7b_vision_analyzer.py`)
already supports an `engine`/`QWEN7B_ENGINE` switch; the same class and both
engine implementations can be pointed at different hardware (any GPU with
compute capability ≥7.5 — Turing/Ampere/Ada/Hopper) without further code
changes. AWQ in particular is expected to work natively there (prebuilt
Triton/CUDA kernels for those architectures are far more commonly available,
and dev headers are not this server's specific constraint). No code or
threshold changes were made to force a different outcome.
